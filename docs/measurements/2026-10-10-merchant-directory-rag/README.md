# 상가(상권)정보 기반 카테고리 힌트 — 측정 기록 (2026-10-10)

거래내역 카테고리화에 소상공인시장진흥공단 상가(상권)정보를 근거로 쓸 수 있는지 판단하기 위해
측정한 원본 기록이다. 포트폴리오 항목은 `docs/PORTFOLIO.md` 의 P-001 을 본다.

## 측정 환경

| 항목 | 값 |
|------|----|
| 측정일 | 2026-10-10 |
| 실행 환경 | Windows 11, Node 24.14.1 (스크립트), 로컬 실행 — 서버·DB 미사용 |
| 원본 데이터 | 소상공인시장진흥공단_상가(상권)정보_20260630 (시도별 CSV 16개, 합계 약 1.42GB, UTF-8) |
| 평가셋 | Financial-Mock-Server `src/main/resources/db/seed-v2-scenario-1.sql` ~ `-5.sql` 의 카드 승인 `ROW(...)` |
| 정규화 규칙 | `MerchantNameNormalizer` 와 동일 (법인 표기 제거 → 한글·영문·숫자만 남김 → 소문자) |
| 기준 코드 | `dev` 7def0ff 시점의 카테고리 파이프라인 (규칙 1~4단계 → LLM) |

평가셋은 실제 영수증 내역을 바탕으로 만든 시드다(사람 확인). 카드사 표기처럼 가맹점명이 잘려 있다
(`지에스(GS)25 화양세`, `엑시트피씨카페(EXI` 등).

원본 CSV(1.42GB)와 집계 CSV(66MB)는 용량 때문에 레포에 넣지 않았다.

## 재현 방법

```bash
# 1) 원본 → 상호명별 업종 분포 집계 (out/merchant_directory.csv, out/industry_codes.csv)
node --max-old-space-size=6144 scripts/aggregate.mjs <원본CSV폴더> <작업폴더>/out

# 2) 평가셋 추출 (가맹점명 \t 시드 카테고리)
grep -ohE "ROW\('[^']*','[0-9-]+ [0-9:]+','[^']+','[0-9]{4}','[^']*'" seed-v2-scenario-[1-5].sql \
  | awk -F"','" '{print $3"\t"$5}' > <작업폴더>/seed_rows.tsv

# 3) 매칭률 측정 → <작업폴더>/match_result.tsv
node --max-old-space-size=4096 scripts/match.mjs <작업폴더>

# 4) 업종→카테고리 매핑 기준 정답률 (industry_category_map.tsv 를 작업폴더에 둔다)
node scripts/eval_map.mjs <작업폴더>
```

## 5. 어휘 검색 vs 벡터 검색 비교

"일반적인 벡터 DB 를 써야 의미가 있지 않느냐"는 질문(사람)에 답하기 위해 같은 평가셋·같은 매핑·같은 채점으로 비교했다.
스크립트: [`scripts/vector_experiment.mjs`](scripts/vector_experiment.mjs), 사례별 결과: [`data/vector_detail.tsv`](data/vector_detail.tsv)

| 조건 | 값 |
|------|----|
| 임베딩 | OpenAI `text-embedding-3-small`, 256차원 |
| 공통 검색 대상 | 2회 이상 등장 상호 252,968 개 (184만 개 전체는 로컬 메모리 한계로 제외) |
| 질의 | 가맹점명을 괄호·접미어·지점명 제거 후 정규화한 문자열 |
| 벡터 검색 | 전수 비교(brute force) 코사인 유사도 |
| 사용 토큰 | 2,066,123 (임베딩 소요 36초, 동시 4요청) |

| 방식 | 힌트 있음 | 소분류 정답 | 정답률(힌트 기준) | 정답률(전체 1,247 기준) | 오답 | 힌트 없음 |
|------|-----------|-------------|-------------------|--------------------------|------|-----------|
| L_sub 어휘 검색 (25만 개) | 923 | 701 | **75.9%** | 56.2% | 196 | 324 |
| V_top1 벡터 1위 (25만 개) | 1,203 | 793 | 65.9% | 63.6% | 333 | 44 |
| V_vote5 벡터 상위5 가중투표 (25만 개) | 1,247 | 795 | 63.8% | 63.8% | 368 | 0 |
| H_sub 어휘 → 못 찾으면 벡터 (25만 개) | 1,198 | 791 | 66.0% | 63.4% | 351 | 49 |
| L_full 어휘 검색 (184만 개, 참고) | 1,073 | 806 | **75.1%** | 64.6% | 224 | 174 |
| H_full 어휘(184만) → 못 찾으면 벡터(25만) | 1,204 | 825 | – | **66.2%** | 약 359 | 43 |

검색 속도(전수 비교): 질의당 29.0ms (25만 개). 184만 개면 선형으로 약 7배 — 운영에는 ANN 인덱스(벡터 DB)가 필요하다.
어휘 검색은 기본키 `IN (...)` 조회 한 번이다.

**같은 거래끼리 비교 (25만 개 범위)**

| 대상 거래 | 건수 | 어휘 정답 | 벡터(1위) 정답 |
|-----------|------|-----------|----------------|
| 어휘 검색이 힌트를 낸 거래 | 948 | 701 | **703** |
| 어휘 검색이 못 찾은 거래 | 299 | (답하지 않음) | 90 (30%) |

**벡터 유사도 임계값별 (1위 유사도가 임계값 이상일 때만 힌트)**

| 임계값 | 힌트 건수 | 정답 | 정답률 |
|--------|-----------|------|--------|
| 없음 | 1,247 | 793 | 63.6% |
| 0.70 | 1,106 | 770 | 69.6% |
| 0.80 | 661 | 529 | 80.0% |
| 0.85 | 503 | 414 | 82.3% |
| 0.90 | 433 | 371 | 85.7% |
| 0.95 | 397 | 346 | 87.2% |
| (참고) 어휘 검색 L_sub | 923 | 701 | 75.9% |

이 표들의 정답률 분모는 "힌트를 낸 건수"이며, 업종 매핑이 없는 힌트도 분모에 포함한다(위 방식 표의 "힌트 있음"과 분모가 조금 다르다).

**해석**
- **"벡터가 덜 정확하다"가 아니다.** 어휘 검색이 답할 수 있는 거래(948건)에서는 벡터도 사실상 같은 정답 수(703 vs 701)를 낸다.
- 정답률 차이는 전부 **어휘 검색이 "없음"이라고 답한 299건**에서 나온다. 최근접 이웃 검색은 DB 에 그 가게가 없어도
  항상 1위를 돌려주므로, 정답이 없는 질의에도 그럴듯한 오답을 붙인다(정답 30%). 예: `캐치유` → `캐치캐치`(0.75),
  `구글플레이` → `원플레이`(0.66), `NICE결제대행` → `대돈단결`(0.61), `LG U+ 통신요금 자동이체` → `대성자동차부분정비공업사`(0.58),
  `세종원` → `세종의원`(0.91, 병원).
- 유사도 임계값을 걸면 벡터도 "모른다"고 답하게 되어 정답률이 오른다(0.80 에서 80.0%, 어휘 75.9% 보다 높음).
  대신 힌트 건수는 661 건으로 어휘(923 건)보다 적다 — 정확도와 커버리지의 교환이다.
- 따라서 어휘 검색을 고르는 근거는 정확도가 아니라 **같은 결과를 기본키 조회 한 번으로 얻는 비용·단순성**이다.
  벡터를 쓴다면 유사도 임계값이 필수다.
- 벡터만 맞힌 사례 상당수는 **같은 가게를 찾은 것이 아니라 이름에 든 업종 단어가 같은 다른 가게**다
  (`카페미엘` → `카페디엘`, `세종로약국` → `세종약국`, `연가카츠` → `연가`). "카페"·"약국" 같은 단어는 LLM 이 이미 해석할 수 있어
  새 정보가 아니다. 진짜 이득은 표기 변형(`앨리스프렌즈` ↔ `앨리스프랜즈`, `메가MGC(인증)` → `메가mgc커피`) 정도다.
- 벡터가 틀린 사례는 **지점명에 끌려간** 경우가 많다 (`본래순대화양점` → `삼성양화점`(패션), `대빵오락실강남점` → `강남식육점`).
  고유명사에서는 브랜드보다 지역명 토큰이 임베딩을 지배한다.
- 결합(H_full, 임계값 없음)은 어휘 단독(L_full) 대비 정답 +19건(64.6% → 66.2%, +1.6%p)이지만, 벡터에서 오는 오답 힌트 약 92건과 벡터 인프라를 함께 들여온다.
  임계값을 건 결합은 측정하지 않았다.
- 정정 기록: 처음에는 위 방식 표만 보고 "같은 범위에서 벡터 정답률이 10%p 낮다"고 해석했으나, 같은 거래끼리 다시 비교해
  원인이 검색 품질이 아니라 기권(abstain) 기준의 유무임을 확인하고 고쳤다(사람이 "왜 정답률이 더 낮은지" 질문해 재분석).

## 6. LLM 전후 비교

구현한 힌트가 LLM 정답률을 올리는지 같은 평가셋으로 쟀다(2026-10-10, 사람이 3회 실행). 러너: `CategorizationHintEvaluationTest` (환경변수가 있을 때만 실행).
원본 결과: [`data/hint_eval_result_run1.tsv`](data/hint_eval_result_run1.tsv), [`data/hint_eval_result_run2.tsv`](data/hint_eval_result_run2.tsv), [`data/hint_eval_result_run3.tsv`](data/hint_eval_result_run3.tsv)
(컬럼: weight, merchant, label, hint, without, with — without/with 는 예측 카테고리명, `null` 이면 분류 불가, hint 가 `-` 이면 힌트 없음).

**무엇을 쟀는가**
- **LLM 단독 정답률**이다. 거래에 `merchantCategoryName` 을 넣지 않았다(시드에서는 그 값이 정답 라벨이라 넣으면 정답이 샌다).
  규칙 1~4단계를 포함한 전체 파이프라인의 정답률이 **아니다**.
- 같은 거래를 「힌트 없음 / 힌트 있음」으로 두 번 분류해 소분류 정답·대분류만 정답·오답·분류불가를 셌다.
  각 회차는 같은 배치에 대해 힌트 없음 → 힌트 있음 순서로 호출했다.

### 이 결과가 말해 주지 않는 것

- 규칙 1~4단계를 포함한 **전체 파이프라인의 정답률이 아니다.** LLM 단독 값이다.

- 업종 매핑과 프롬프트를 **이 평가셋을 보면서 설계**했다. 따로 떼어 둔 검증셋(held-out)이 없어 힌트 있음 값이 낙관적일 수 있다.
- 힌트 없음 조건은 임계값(0.81)에 걸려 `null` 이 되는 비율이 높다. 임계값을 낮추면 달라질 수 있으나 측정하지 않았다.
- 평가셋 라벨(시드)에도 모호한 경우가 있다(장난감 소매, 다이소).

## 측정하지 않은 것

- **규칙 1~4단계 + LLM 전체 파이프라인의 같은 평가셋 정답률** — 6절은 `merchantCategoryName` 을 비운 LLM 단독 값이다.
- **카드사 업종명(MCC)이 있는 실제 거래** — 시드에서는 MCC 값이 정답 라벨이라 비웠다. 실제로는 상당수가 3단계 MCC 규칙에서 이미 분류될 수 있어, 힌트의 실제 순이익은 MCC 가 없는 거래(계좌이체·페이머니)에서 따로 측정해야 한다.
- 실제 사용자 거래 중 LLM 단계로 넘어가는 비율 — 로컬 DB 접속 실패로 측정하지 못했다. 실사용 거래에서의 힌트 효과도 측정하지 않았다.
- 4회 이상 반복 실행, temperature 고정 실행 — 현재는 3회뿐이고 회차 간 변동이 보인다.
- held-out 평가 — 매핑·프롬프트 설계에 쓰지 않은 거래로의 검증.
- 벡터 검색의 184만 개 전체 대상 측정, 차원 수(256 외)·다른 임베딩 모델 비교, 임계값을 건 어휘+벡터 결합.
