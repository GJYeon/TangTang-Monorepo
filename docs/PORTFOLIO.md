# PORTFOLIO — 작업 기록

포트폴리오·자기소개서에 바로 옮겨 쓸 수 있도록 **의미 있는 작업 단위마다** 기록한다.
`DECISIONS.md`는 Agent가 지킬 결정을 짧게 남기는 곳이고, 이 문서는 **왜 그렇게 판단했는지와 어떤 결과가 나왔는지**를 남기는 곳이다.

## 작성 규칙
- 작업 단위(기능 하나, 버그 묶음 하나, 구조 개선 하나)가 끝나면 Claude가 초안을 쓰고 사람이 확인한다. 확인 전에는 제목에 `(초안)`을 붙인다.
- **판단 이유는 지어내지 않는다.** 사람이 직접 말한 이유만 적고, 모르면 `[확인 필요]`로 남겨 사람에게 묻는다.
- **효과는 측정값으로 적는다.** 작업을 시작하기 전에 "변경 전" 수치를 기록해 둔다 (예: 응답 시간, 외부 API 호출 수, 실패율, 테스트 수, 중복 레코드 수, 코드 줄 수). 측정하지 못했으면 `[측정 안 함]`이라고 쓰고 추정치를 쓰지 않는다. 측정 환경과 원본은 `docs/measurements/`에 두고 링크한다.
- 관련된 `DECISIONS.md` 번호(D-xxx)와 `ISSUES.md` 번호, 커밋 해시를 함께 남긴다.
- 사람이 판단한 부분과 AI에게 맡긴 부분을 구분해서 적는다.

### P-001 (초안): 공공 상가정보 1.42GB 를 거래 카테고리화 근거(RAG)로 쓰기 위한 사전 검증
- 기간: 2026-10-10 ~ (진행 중 — 구현 완료 (로컬), LLM 전후 비교 3회 측정 완료, 사람 검토 대기)
- 관련: D-xxx 없음, 이슈 [확인 필요 — #481 거래내역 카테고리 고도화의 후속인지], 기준 코드 `dev` 7def0ff, 측정 [docs/measurements/2026-10-10-merchant-directory-rag](measurements/2026-10-10-merchant-directory-rag/README.md)

**문제 상황 (Situation)**
- 거래 카테고리화는 규칙 4단계(사용자 매핑 → 가맹점 매핑 → 카드사 업종명 → 키워드)를 거쳐, 모두 실패한 거래만 LLM(OpenAI)에 넘긴다.
- LLM 은 가맹점명만 보고 자기 상식으로 추론한다. 체인 브랜드는 잘 맞히지만 **동네 가게처럼 모델이 모르는 상호**는 근거 없이 추측하거나 `null` 을 돌려준다.
- 사람이 전국 상가정보 CSV(소상공인시장진흥공단, 2026-06 기준)를 확보했고, 이를 RAG 로 활용하면 정확도를 올릴 수 있다고 판단했다.
- 처음 우려는 **용량(1.42GB)** 이었다(사람 언급).

**판단 기준**
- 효과를 **측정으로 먼저 확인**하고 구현한다 — 근거 없이 수백만 행을 서비스 DB 에 넣지 않는다.
- 팀 고정 스택(Spring Legacy · MyBatis · MySQL 8) 안에서 해결한다 — 벡터 DB 등 인프라를 추가하지 않는다.
- 6인 팀이 같이 쓰는 레포이므로 원본 대용량 파일을 커밋하지 않는다.
- 그 밖에 사람이 우선한 기준 [확인 필요]

**대안 비교**
| 대안 | 장점 | 단점 |
|------|------|------|
| A. 임베딩 벡터 RAG | 표기 변형에 유연, 임계값 0.8 에서 정답률 80.0% | **실측** 어휘가 찾는 거래에선 정답 수 동일(703 vs 701) — 이득이 없고, 임계값 없이는 없는 가게에도 오답을 붙임(정답률 63.6%), 벡터 DB(ANN) 추가 필요 |
| B. 상호 사전 조회 결과로 **바로 확정** | LLM 호출 절감, 결정적이라 테스트 쉬움 | 측정 결과 정밀도 85%(정확 일치) — 동명 상호·법인명 오매칭을 그대로 확정하게 됨 |
| C. 상호 사전 조회 결과를 **LLM 프롬프트 근거(힌트)로 주입** | 틀린 힌트를 LLM 이 걸러낼 수 있음, 커버리지 89% 활용 가능 | 프롬프트 설계 필요, 효과는 LLM 기준선과 비교해야 확인 가능 |
| (용량) 원본 적재 vs 집계 적재 | 집계 시 66MB(gzip 19MB)로 축소 | 등장 1회 상호(86%)는 비율이 항상 100% 라 신뢰도 판단 불가 |

**결정과 이유**
- 검색 방식은 **어휘 기반(정확 일치·앞부분 일치)** 으로 정했다. 사람이 "일반적인 벡터 DB 를 써야 의미가 있지 않느냐"고 문제를 제기해, 추측 대신 같은 평가셋으로 벡터 검색과 비교 실험을 했다(사람 결정). 처음 표에서는 벡터 정답률이 낮아 보였지만(65.9% vs 75.9%), 사람이 "왜 더 낮은지" 다시 물어 같은 거래끼리 재분석했다. 어휘 검색이 답한 948건에서는 벡터도 정답 수가 같았고(703 vs 701), 차이는 전부 DB 에 없는 가게에도 최근접 이웃을 답으로 내는 **기권 기준 부재**에서 나왔다(유사도 임계값 0.8 이면 80.0%). 즉 이 데이터에서 벡터는 어휘 검색보다 정확하지도 않고, 같은 결과를 얻는 데 인프라만 더 든다. 최종 채택 여부는 사람 확인 [확인 필요].
- **C. LLM 프롬프트에 근거로 주입**을 진행하기로 했다(사람 결정). 정밀도 85% 신호로 바로 확정하면 현재 LLM 보다 나빠질 수 있다는 측정 결과를 근거로 했다.
- 용량 문제는 **원본을 오프라인에서 한 번 집계**해 `상호명 → 최다 업종·건수·비율` 만 남기는 방식으로 해결했다(1.42GB → 66MB).
- 힌트를 업종명이 아닌 **우리 표준 카테고리로 매핑한 뒤** 쓰기로 했다 — 사람이 매핑을 먼저 해달라고 요청했다. 이유 [확인 필요]
- 평가셋은 **실제 영수증 기반으로 만든 목서버 시드**(시나리오 1~5)를 쓰기로 했다(사람 판단). 로컬 DB 접속이 막혀 실사용 거래로는 측정하지 못했다.
- 감수한 트레이드오프: 1회 등장 상호(86%)를 남겨 커버리지를 지키는 대신, 이들은 비율로 신뢰도를 걸러낼 수 없다.

**한계와 개선점**
- LLM 전후 비교는 **「LLM 단독 정답률 (`merchantCategoryName` 제외)」** 이며 규칙 1~4단계를 포함한 전체 파이프라인 정답률이 아니다.
- **트레이드오프**: 분류 불가가 크게 줄어드는 대신 힌트가 오도한 **오답이 약 4.2% 새로 생긴다**(힌트 없을 때는 0~3건). 답한 것 중 소분류 정답 비율은 약 99~100% → 약 91~92%.
- **3회만 실행**했고 회차 간 변동이 크다(힌트 없음 20.3% ~ 28.6%, 힌트 있음 49.7% ~ 52.5%). 세 회차 모두 힌트 있음이 24%p 이상 높다는 방향은 일관된다. 힌트가 붙지 않은 가맹점에서도 결과가 갈리는 사례가 있어 모델 응답 변동이 관찰된다.
- 업종 매핑과 프롬프트를 **같은 평가셋을 보면서 설계**했다. 따로 떼어 둔 검증셋(held-out)이 없어 측정값이 낙관적일 수 있다.
- **전체 파이프라인의 개선 전 기준선이 없다.** LLM 단독 값만 쟀으므로 규칙 1~4단계를 포함한 현재 파이프라인의 정답률 향상은 주장할 수 없다.
- 앞부분 일치 오답의 대부분(약 110건)은 플랫폼·PG 명(카카오T, 네이버페이, 티머니)이 잘려 엉뚱한 상호에 걸린 것이다 → 플랫폼·PG 키워드 규칙을 앞 단계에 추가하면 해소될 것으로 보인다.
- 평가셋 시드에는 카드사 업종명(MCC)이 붙어 있어(전후 비교에서는 정답이 새므로 비웠다), 실제 운영에서는 상당수가 MCC 규칙 단계에서 이미 분류될 수 있다. 진짜 순이익은 MCC 가 없는 거래(계좌이체·페이머니)에서 측정해야 한다. 실사용 거래에서는 측정하지 않았다.
- 힌트가 틀린 업종일 때(카카오 → 주점 등) LLM 이 정답을 버리고 `null` 로 물러나거나 힌트를 따라 오답을 낸다 — 플랫폼·PG 규칙 선행이 필요하다.
- 시드 라벨 자체가 일관되지 않은 경우가 있다(같은 다이소가 편의점·생활용품으로 혼재).
- 매핑표 일부 판단(주점 → 음식점/외식, 핸드폰 소매 → 쇼핑 등)은 팀 합의가 필요하다.

- **추가 분석 (측정 문서 7절, 4회차 1회 기준)**: 사람이 "정답률이 낮은데 벡터 DB·모델 학습이 필요한가"를 물어, 원인을 먼저 쪼개 봤다.
  - 낮은 정답률은 오답이 아니라 **분류 불가(null)** 때문이다. LLM 은 힌트를 거의 그대로 따른다 — 맞는 힌트(806건)를 받으면 답한 것은 전부 정답, 틀린 힌트(267건)를 받으면 정답 0건. 병목은 검색 방식이 아니라 **힌트 품질과 임계값**이다.
  - 모델 confidence 가 0.8·0.9 같은 계단 값이라 운영 임계값 0.81 이 "0.8" 답을 전부 버린다. 같은 응답에 임계값만 바꾸면 힌트 있음 정답률이 0.81 에서 50.5%, 0.80 에서 54.8%, 0.70 에서 58.3% 이고 오답은 3.8% → 5.3% → 5.8% 로 늘어난다. 운영 임계값은 바꾸지 않았다 [확인 필요 — 팀 결정].
  - **프롬프트 부작용 발견**: 힌트 있음 조건에서는 힌트가 붙지 않은 거래(146건)에 모델이 확신도를 0 으로 줘, 힌트 없이 맞히던 18~25건이 1건으로 줄었다(4회 모두 동일). 6절에서 "모델 변동"으로 적었던 해석을 정정했다. 아직 고치지 않았다.

**한 줄 요약 (자소서용)**
- (초안) "LLM 이 모르는 동네 상호의 분류 근거가 없는 문제를 측정 우선 원칙으로 접근해, 공공 상가정보 1.42GB 를 66MB 사전으로 압축하고 벡터 검색과 어휘 검색을 같은 실영수증 평가셋으로 비교해 정확도 차이가 검색 품질이 아니라 기권 기준 유무에서 온다는 것을 밝힌 뒤(같은 거래 정답 703 vs 701), 인프라 추가 없이 같은 결과를 내는 어휘 기반 RAG 로 LLM 프롬프트에 근거를 주입. LLM 단독 소분류 정답률 23.8% → 50.9% (3회 평균, MCC 제외), 미분류가 크게 줄어든 대신 오답 약 4.2% 가 새로 생기는 트레이드오프를 확인" — 3회 실행·같은 평가셋으로 설계(held-out 없음)·전체 파이프라인 미측정이라 수치 사용 시 이 조건을 함께 적을 것
